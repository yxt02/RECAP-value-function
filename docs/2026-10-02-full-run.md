## 2026-10-03 throughput tuning

The model processes three camera streams and a Gemma prefix per frame. The sole task prompt tokenizes to 16 tokens, while the old configuration padded it to 200. The replacement uses 32 tokens. Short two-GPU runs measured `train_seconds` within the epoch and peak reserved memory on GPU 0:

| Per-GPU batch / accumulation | Workers | Checkpointing | Samples | Train time | Peak GPU |
|---|---:|---|---:|---:|---:|
| 2 / 2, 200 tokens | 0 | on | 128 | 20.5 s | 9.6 GiB |
| 4 / 1, 200 tokens | 0 | on | 128 | 12.1 s | 10.4 GiB |
| 8 / 1, 200 tokens | 0 | on | 256 | 15.5 s | 14.8 GiB |
| 8 / 1, 32 tokens | 0 | off | 256 | 13.4 s | 20.1 GiB |
| 16 / 1, 32 tokens | 0 | on | 512 | 22.5 s | 21.3 GiB |

For 1024 training samples at batch 8 with checkpointing off, 0/2/4 workers took 52.1/47.4/51.6 seconds. A 1024-sample validation window took 13.8 seconds with 0 workers versus 10.6 seconds with 2. The selected configuration is batch 8, accumulation 1, two workers for each loader, 32 task tokens, and checkpointing off. Its global effective batch of 16 matches the original planned configuration; peak GPU memory was about 20 GiB, leaving substantial headroom. The training loop now records per-epoch durations and peak reserved GPU memory and reports progress every 50 optimizer steps.
